# Follow-up filter optimization plan

Date: 2026-10-14
Status: Filter roster assessed. V01–V14 and A01–A51 have outcomes. Retained experimental candidates include V05 and CPU optimizations A14, A24, A27 and A46. Transient (A42) and Multiband (A44) speed edits were discarded because their app-screen p95 gains did not meet the 10% selection gate. Current no-argument routing automatically selects eligible GPU implementations by rack composition; performance acceptance remains separate. Deferred work is listed per filter.
Baseline: [`APP_OPTIMIZATION_SPEC.md`](APP_OPTIMIZATION_SPEC.md), current working tree, and the accepted local R3 route.

## 1. Goal

Work through every filter that is not already in the accepted accelerated route, one at a time. Keep the current JavaScript CPU filter as the reference and usable implementation. For each filter, produce one of these reviewed outcomes:

1. an optional accelerated implementation (GPU for video where the complete app route can stay GPU-resident; WASM or another measured CPU technique for audio when appropriate), with the CPU implementation retained; or
2. a documented no-go explaining why acceleration is unsuitable, incorrect, or slower for the complete app workload.

“GPU-capable” means a correct application route, including capture/input conversion, state, presentation or audio submission, and fallback. A fast shader/kernel alone does not qualify. A no-go is a completed assessment; it is not a reason to weaken output parity or force a GPU route.

The existing R3 route (`TapeSat -> Procamp -> Solarizer -> Colorizer`) stays intact as a reference accelerated route throughout this follow-up. The application now selects an eligible GPU route automatically when no backend is specified, using the resolved rack chain and the GPU capability inventory. This is static route planning, not per-frame backend switching or a worker/audio-scheduling redesign. Production deployment remains separate.

## 2. Rules carried forward

- Keep the current CPU code, state transitions, parameter ranges, RNG behavior, resets, processing order and output conversions as the oracle. Do not change the artwork to make a candidate easier to port.
- Start from `docs/APP_OPTIMIZATION_SPEC.md` sections 3–8. Its parity requirements, fixed workloads, budgets and stop conditions continue to apply. This follow-up scopes new candidates; it does not reopen failed or deferred work automatically.
- Work on a clean, attributable snapshot or preserve the user's current dirty worktree. Never stage, reset or revert the pre-existing optimization edits as a group.
- Finish and record one candidate before starting the next. Do not run a sustained acceptance cohort for every filter. Run correctness fixtures for each candidate; profile and screen only where a complete application workload can use it.
- Keep parity and capability separate from performance acceptance. A candidate without parity remains unavailable. A parity-correct GPU filter may be selected automatically when the rack can compose it into a supported resident segment, even when its solo speed ties CPU; report performance acceptance separately and retain explicit CPU/GPU overrides for comparisons.
- Do not claim a filter is “GPU accelerated” based on standalone timing. Report per-filter kernel cost separately from complete-route benefit, transfer cost, CPU fallback behavior, and production status.
- Keep GPU implementation capability separate from the selected route. A parity-correct filter can remain in the shared GPU capability inventory when its standalone speed ties CPU, because adjacent supported filters can share one resident frame and avoid inter-filter transfers. With no backend argument, select the best eligible GPU segment from the chain; use CPU when the route constraints or fidelity check fail. Performance acceptance remains a separate report status.
- Retain a CPU optimization only when its measured application-path improvement meets the section 7 gate: paired median p95 improves by at least `max(2 ms, 10% of baseline p95)`, at least two of three pairs improve, and the remaining throughput/fidelity constraints pass. If a screening result is below that gate, revert the speed edit and keep the reference implementation.
- Use existing harnesses and tests. Add only focused fixtures needed for that filter and shared executor. Run the consolidated suite once for an integration group, with affected-only retries after fixes.

## 3. One-filter work contract

Use this same bounded sequence for every roster item.

### F0 — Freeze and profile

1. Record the filter ID, code revision, relevant files, current CPU implementation and a focused real-app rack that contains it.
2. Add/freeze a deterministic fixture if the existing fixture set does not cover its defaults, boundaries, parameter changes, multiple frames and state transitions. Hash the fixture/source.
3. Make one short profiling pass with profiling disabled for later comparisons. Identify whether the work is CPU DSP, CPU pixel work, upload/readback, synchronization, capture, or presentation. If the filter is not material to a real slow rack, document that result and stop at CPU-only.
4. Choose the candidate backend based on the whole dataflow. Video may use GPU only when neighboring work and presentation avoid per-filter transfers. Audio normally stays on CPU; consider WASM only for a deterministic, supported CPU segment when the cost of copies/calls is justified.

### F1 — Implement an optional candidate

1. Add the candidate behind the existing route/coordinator boundary; keep the original CPU implementation directly selectable.
2. Reuse the shared device, command submission, frame resources and route infrastructure. Do not create a device or allocate/map a full frame per filter or per frame.
3. Match the original operation order and intermediate quantization. Preserve per-instance state, initialization/reset rules, same-frame audio modulation, parameters and randomness. Define explicit state ownership and a frame-boundary fallback before integration.
4. Do not add automatic cost-based routing. Add the filter to an explicit eligible rack only after its correctness gate passes.

### F2 — Correctness gate

Run the smallest affected Node/conformance checks, deterministic per-filter fixtures and a short composed-rack browser check where the app path changes. Include identity/default, parameter extremes and rounding boundaries, alpha/format behavior where applicable, repeated instances, order, changed parameters, consecutive frames, reset/reorder/bypass, source change and disposal. Use the exact filters' applicable subset; do not construct an unnecessary Cartesian matrix.

Require byte-exact video parity where the reference is byte-defined. Audio tolerances must come from the existing conformance contract for that filter and include its relevant state. Never raise tolerance to make a candidate pass. Stop on a mismatch; allow no more than two substantive repair cycles, then record DEFERRED/FAILED and keep CPU selected.

### F3 — Performance decision

1. If F0 shows plausible whole-route impact, run one existing-harness screen: 10 s warmup plus 15 s measured per AB/BA order, with actual app audio/HUD and inclusive frame-path timing. Use the matching CPU rack as baseline.
2. Continue only when fidelity passes and the app route shows a useful, repeatable improvement without a material regression elsewhere. Kernel-only speed does not pass this gate.
3. For an ambiguous result, use at most one acceptance cohort (three pairs, AB/BA/AB, 10 s warmup plus 60 s measured) or defer. For a winner, use one 300 s confirmation only when required by the parent spec for a new winning route/workload. The parent spec's overall acceptance limits remain in force.
4. A measured loss, marginal gain below the parent spec benefit gate, parity failure, excessive transfers, unbounded resource growth, or exhausted budget ends this candidate. Keep CPU selected and move to the next roster item.

### F4 — Record and hand off

Update the ledger below with: implementation files; checks and outcomes; CPU-versus-candidate route; parity/status; performance evidence or why no screen was justified; fallback and device limitations; production status; next exact filter. Use distinct outcomes: `CPU ONLY`, `IMPLEMENTED - VERIFY`, `VERIFIED EXPERIMENTAL`, `ACCEPTED PERFORMANCE ROUTE`, `DEFERRED`, `FAILED`.

## 5. Integration gates

Do not expose a general route for every possible combination. Build explicit supported rack families in small groups.

1. **Video extension group:** first candidate from V01–V11 that passes parity and can join a real app workload. Confirm ordered composition with R3, CPU fallback on unsupported formats/resolutions/camera/recording, and no extra full-frame transfer between GPU nodes. A single-filter win is useful evidence for prioritization, not proof of an optimized multi-filter route.
2. **CPU-audio group:** only after profiling identifies a material CPU DSP workload. Compare the full compatible audio segment against JavaScript. Preserve 8192-sample chunking, node order, parameter/reset semantics and persistent state. Do not add generic partial JS/WASM splitting without separate evidence and approval.
3. **Combined rack:** test a video extension plus an audio candidate only if both independently pass and they share a supported capture, device, frame and state model. Require one whole-rack parity and screen result before enabling the combination.
4. **Regression:** keep R0/R1/R3 comparisons and fallback/browser transition checks. Report route, bytes copied/read back, dispatch/map count, p95/FPS, fidelity, device/build and fallback reason.
5. **Rollout:** experimental routing stays opt-in. Production deployment is a separate user action after local verification; report it independently from code completion and benchmark results.
